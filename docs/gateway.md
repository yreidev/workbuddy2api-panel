## 请求的一生

```mermaid
flowchart LR
    C["客户端<br/>OpenAI 兼容请求"] --> H["鉴权 · 解析模型名<br/>提示词改写 · 指纹脱敏"]
    H --> S{"会话已绑定<br/>且账号健康?"}
    S -- 是 --> U
    S -- 否 --> P["账号池选号<br/>优先级 · 成本分层 · 加权随机"]
    P --> U["上游请求<br/>强制 stream:true"]
    U -- 成功 --> R["重建 SSE 帧<br/>还原工具调用"] --> C
    U -- 失败 --> E["错误分类<br/>冷却 / 熔断 / 不罚号"] --> P
```

1. **鉴权**：`api_key` 非空时校验 `Authorization: Bearer <api_key>`（常量时间比较）。
2. **解析模型名**：`cn:` / `global:` 前缀决定去哪一域选号；不带前缀时默认走国内版，打开跨域负载均衡后两域合池。
3. **改写请求**：按 `prompt.mode` 处理系统提示词，清洗指纹串，补齐推理参数，统一 `developer` 角色、`tool_choice` 与 `image_url` 的写法；历史里配不上对的工具调用、工具名为空的工具调用连同结果一起剔除，消息内容里的思考片段（`reasoning_text`、`reasoning`，经 new-api 之类把 Responses 转成 Chat 的中转进来时会带着）也去掉，免得上游拒收整个请求（思考片段上游回 `11101`）。
4. **选号**：会话已绑定且账号健康就直接用；新会话先分配一个账号绑定（见[会话粘性](#会话粘性)）；没有会话键、或绑定的账号这次用不了时，从池里挑。客户端密钥限定了账号分组时，只用组里的号（见[选号策略](#选号策略)）。
5. **转发**：出站一律 `stream:true`；客户端要非流式时，网关在本地把整段流聚合成一个响应。
6. **出错换号**：按错误类型决定是否惩罚账号，然后换一个账号重试。号的代理连不上（连不上代理、代理认证失败、代理拒绝转发）不算号的错，也不算官方入口的错：不罚号、不切入口、不记熔断，代理标成不通、绑在上面的号暂停选号，直接换号，见[按号代理与代理池](proxy.md#代理不通)。

## 选号策略

1. **过滤**：去掉禁用、暂停选号、冷却中、熔断中、在途已满的账号，这个模型在号的「不接的模型」名单里的账号，以及被[代理池](proxy.md)拦着的号（代理不通、到期、在等代理、开着「只许走号的代理」却没绑）；企业号只接自己模型目录里有的模型，企业专属模型只派给目录里有它的企业号（见[企业版模型](tasks.md#禁用暂停与企业版账号)）。
2. **优先级分层**：每个号有一个优先级（面板账号详情里设，0～99，越小越先用，默认 0）。只在优先级最高、此刻能接这个请求的那一层号里挑；这一层的号都接不了（冷却、禁用、暂停、这个模型冷却、积分保底拦着、在途或每分钟请求数满了）才轮到下一层。号都是默认的 0 时就是一层，和以前一样。参考了 [Wei-Shaw/sub2api](https://github.com/Wei-Shaw/sub2api) 账号的 `priority`。
3. **成本分层**：账号对同一个模型的实测扣费可能不同（有的账号有免费额度）。网关按实测把账号分成三层——实测免费、尚无观测、实测收费——只在当前最优的一层里挑。先分优先级层再分成本层：高优先级的号实测收费、低优先级的号免费，照样先用高优先级的号。
4. **积分保底**（`pool.credit_floor`，默认关）：余额低于保底值的账号不再接**实测收费**的模型，避免把余额打穿到连免费模型都用不了；免费层和无观测层不受影响。签到回血越过保底值后自动恢复。全池都触底时返回 503，不会放行。
5. **快过期加权**（`pool.prefer_expiring`，默认开）：窗口内（默认 7 天）有积分快过期的账号，权重 ×3。这是软偏好：不按到期先后排序，也和金额无关，弱于会话粘性、优先级和成本分层。到期时刻照官方客户端按包类型取：签到、任务发的活动包和加油包看失效时刻（`DeductionEndTime`），每日免费包和订阅、体验这类按周期刷新的包看刷新时刻（`CycleEndTime`），详见[对齐文档](official-client.md#积分包的到期时刻)。
6. **加权随机**：`权重 = 积分占比 × 10 + 闲置补偿`。积分占比是该账号积分除以候选里的最大积分；闲置补偿每闲置一小时加 `idle_weight_per_hour`，封顶 `idle_weight_max`，从未用过的账号直接给满。按权重取前 5 个候选再随机。
7. **防惊群**：刚被选中的账号短时间内跳过；全部账号都在冷却时，从软冷却或熔断的账号里挑最早到期的顶上。

**客户端密钥限定账号分组**：面板「账号池」下方可以建账号分组（一个号可以在好几个组里），[客户端密钥](api.md#客户端密钥)可以勾上几个分组。用这样的密钥的请求只用这些组里的号：选号、换号重试、排队、会话粘性、回到用过的号、全冷却兜底、联网搜索都不碰组外的号；组里的号都接不了时回 503，错误信息是 `no account in this API key's groups can take this request right now`，`gateway_hint` 以 `key_groups` 开头（组里的号只是在途满了时照常排队，等满回 `all accounts are busy`）。没勾分组的密钥、管理员密钥、没开鉴权的请求照常用全部的号。分组本身不影响选号的先后，先用哪个号看优先级。参考了 [Wei-Shaw/sub2api](https://github.com/Wei-Shaw/sub2api) 的账号分组和 API 密钥绑分组。

**成本探索**（`pool.cost_explore_interval`，默认 30 分钟）：如果免费层一直有号可用，尚无观测的账号就永远学不到真实成本。所以每个窗口会把一个真实请求改道给尚无观测的账号——不额外发请求，成功就完成学习，失败按正常错误处理。

**每号每分钟请求数**（`pool.max_rpm` 管国内版、`pool.max_rpm_global` 管国际版，默认 `0` 不限）：一个号最近 60 秒内接到的请求数到了上限，就和在途占满一样当它忙：选号跳过它，粘性号到了上限也换别的号，能接的号都忙时排队（见下一段）。按滑动的 60 秒算，不会在分钟交界处一下子放出两倍；换号重试、测活都算一次请求。计数不落盘，重启后从零算；不限的时候不计数，打开上限后才开始算。想压低单号的请求频率时用，比如同一出口 IP 下号多、担心上游按频率风控；腾讯是否按频率风控未确认。上限设得太低，请求会频繁排队、等满回 503。参考了 [Wei-Shaw/sub2api](https://github.com/Wei-Shaw/sub2api) 账号的 `base_rpm`，只是不给已绑定的会话留缓冲。

**号都满时排队**（`pool.in_flight_wait`，默认 30 秒）：能接这个请求的号都健康、只是在途都满了（或每分钟请求数到了上限）时，请求不马上回 503，而是等其中一个号放出名额再选号，一个请求合计最多等这么久，等的时间不算换号次数。等满仍没有空位才回 503，错误信息写明是号都在忙（`all accounts are busy`，`gateway_hint` 以 `in_flight_full` 开头；有号是因为每分钟请求数到上限时以 `rpm_full` 开头）。粘性号满了照旧换别的号，只有所有能接的号都满了才排队；号用不了是因为冷却、禁用、暂停、模型级冷却或积分保底时不排队，照旧马上回错。排队期间不给客户端发任何数据，流式请求的首字时间会算上排队的时间。上游回 `6020` 把请求排进它的容量队列时，在那个号上等到号也用这个上限，见下文「错误分类与账号处置」。设成 `0` 回到以前的做法：选不到号直接 503，上游排队也不等。30 秒参考了 [Wei-Shaw/sub2api](https://github.com/Wei-Shaw/sub2api) 的 `fallback_wait_timeout`。

## 跨域负载均衡

`pool.cross_realm` 管不带前缀的模型名怎么在国内版和国际版之间分。打开后 `/v1/models` 会多列出一份不带 `cn:` / `global:` 前缀的模型名，用这种名字请求时网关自动在国内版、国际版账号里选号；带前缀的名字照旧只走那一域，前缀并没有去掉。有三档：

| 取值 | 做法 |
|---|---|
| `off`（默认） | 一律走国内版 |
| `merge`（合池） | 国内版和国际版账号合成一个池，按上面的选号策略挑 |
| `cn_first`（国内版优先） | 国内版此刻有能接的号就只在国内版选，没有才用国际版 |

老配置写的 `true` 读成 `merge`、`false` 读成 `off`，不用改。

`merge` 和 `cn_first` 都先按两个域的模型目录分流：

| 情况 | 去向 |
|---|---|
| 两个域都有这个模型 | 按上面那一档在两个域之间分 |
| 只有一个域有 | 只在那个域选 |
| 两边目录都没有（目录没拉到，或模型名写错） | 走国内版，和 `off` 一样 |

国内版优先时，「国内版此刻没有能接的号」指国内版的号都在冷却、禁用、暂停、这个模型冷却、被积分保底拦下，或者在途都满了；这次请求已经试过的号不算，客户端密钥限定了分组时组外的号也不算。这时请求直接改到国际版，不排队等国内版。国际版也没有能接的号时照合池处理：两个域的号一起参与全冷却兜底和排队，排队期间哪个域先放出名额就用哪个。每次换号、排队醒来都重新判一次，所以国内版的号这次失败了，同一个请求会接着换到国际版；绑在国际版号上的会话，等国内版又有能接的号了，下一次请求就回到国内版，先回这段对话用过的国内版号。

补充说明：

- 带前缀的模型名不受影响，想钉死某一域照旧加前缀。
- 模型目录启动时拉一遍，之后没拉到的域每分钟补拉一次，拉到的每 30 分钟刷新，调 `/v1/models` 时也会刷新；某次拉取失败沿用上次成功的目录。还没拉到目录的域当作没有这个模型，不往那边分。
- 积分保底和用量统计里的积分倍率都按实际服务的账号所在域计算（同一模型两域倍率可能不同）；请求日志的模型列写成 `域:模型名`。
- `/v1/models` 会在最前面额外列出不带前缀的名字（两域并集去重，`realms` 字段标出会分到哪些域），`merge` 和 `cn_first` 都列。
- 会话粘性：合池时在两个域合起来的号里分配，新会话可能绑到国际版号，也可能绑到国内版号，已经绑定的会话不因打开合池而换号；国内版优先时只在这次该用的那个域里分配。改回 `off` 后，绑在国际版号上的会话下一次请求改回国内版。
- 成本分层是硬过滤，从池里挑号的请求（没有会话键，或绑定的号这次用不了）和新会话的绑定都只在最便宜的一层里挑。合池时，某模型在一个域实测免费、另一个域收费，请求会先全部落到免费那一域，那一域的号都占满或冷却了才轮到另一域；已经绑定的会话不因此换号。国内版优先先定域，再在这个域里按优先级、成本分层，不会因为国际版免费、或者国际版的号优先级更高就把请求挪过去。
- 需要同时启用国际版（`global.enabled`）。面板「配置 → 账号池与流量治理 → 选号权重」里可以选，保存即生效。

## 会话粘性

同一会话尽量用同一个账号，多轮对话不跳号：

- **会话键**：依次取 `metadata.conversation_id`、`metadata.conversationId`、顶层 `conversation_id`、顶层 `conversationId`、`prompt_cache_key`。
- **没有会话键时**：用「系统提示词 + 第一条用户消息」的哈希作为会话键，普通 OpenAI 客户端也能享受粘性；请求带了 `metadata.user_id` 时不这样推算。
- **新会话分给哪个号**：先按[优先级](#选号策略)只留最高、此刻能接的一层，再按[成本分层](#选号策略)只留最便宜的一层（含成本探索），再在里面按会话键哈希挑一个，优先还没绑定任何会话的号；这一步不看积分权重。已经绑定的会话照旧用原来的号，免费号出现也不挪走，免得丢掉上游的前缀缓存。跨域负载均衡设成合池时，可用账号是两个域合在一起的；国内版优先时是这次该用的那个域的。
- **回到用过的号**：有的模型的前缀缓存按号存（如 `deepseek-v4.1-flash`，见下一条），换到别的号，这一轮要整段重算。网关给每段对话记下最近成功用过的 3 个号（最后一次成功后保留 7 天，和下面的会话 id 一起存盘）。绑定没了要重新分配时（闲置超过有效期、请求失败解绑、网关重启），先回到其中还能用、又在优先级最高那一层的号，最近用过的优先，不受成本分层限制（同已绑定的会话）；绑定的号这次用不了、要换号重试时，也先试这几个号。都用不了，才按上面的规则挑新号。这个做法参考了 [ardeyouxipianyi/workbuddy2api-hub](https://github.com/ardeyouxipianyi/workbuddy2api-hub)。关闭会话粘性时不记。
- **回到高优先级的号**：优先级高的号都忙时，会话会落到低一层的号上。等高一层的号又能接了，下一次请求就回到高一层，先回这段对话在那一层用过的号，没有才在那一层重新分配。这一点和成本分层不同：成本分层不挪已经绑定的会话，优先级会挪，免得备用号一直被占着。
- **客户端密钥限定了分组**：已经绑定的号不在密钥的分组里时不用它，在组里重新分配；两把分组不同的密钥发同一段对话，会互相改绑，只是缓存接不上。
- **出站的会话 id（`X-Conversation-ID`）**：官方客户端整段对话都用同一个会话 id。上游的前缀缓存有的模型按号存，有的按会话 id 存：
  - 2026-10-28 在生产国内版实测 `glm-5.3-flash`（前缀约 1 万 token）：同一个会话 id 在原来的号上 4/4 命中，换到别的号上也 4/4 命中；换新 id，同一个号 0/3、别的号 0/9。所以它跟着会话 id 走，不认号。10-27 测出的「要同一个号、同一个会话 id 才命中」是把换号和换 id 放在一起测了，号的那一半不对；同 id 闲置 2、5、10、20 分钟都还命中（10-27 测的）；
  - `deepseek-v4.1-flash` 按号缓存，跟会话 id 无关（10-27：同一个号换新 id 3 次都命中，换号 1 次未命中，样本少）；
  - 2026-10-19 用个人免费号实测：`glm-5.2` 会话 id 稳定时第二轮 8 次全部命中，每轮换新 id 只命中 3/10，未命中的一轮扣 0.63 积分、命中的扣 0.17；`deepseek`、`kimi`、`glm-5.3` 不论会话 id 都能命中；
  - 企业号和付费号没测过。

  客户端在请求体里给了 `conversation_id` 就原样转发。没给时网关按内容认对话，同一段对话的会话 id 不变：
  - 第一轮（历史里还没有助手回复）按「系统提示词 + 第一条用户消息」生成并记下一个会话 id；
  - 出现第一条助手回复后，这段对话接着用第一轮记下的 id，此后不再变。如果这个 id 已经被开头逐字相同、但第一条回复不同的另一段对话用上了，就给这段对话另起一个。所以开头逐字相同的两段对话（比如中转站的渠道测试）第一轮共用一个 id，第二轮起分开。2026-10-19 在两个域用 `deepseek-v4.1-flash`、`glm-5.2`、`glm-5.3`、`kimi-k2.8-preview` 实测过，2026-10-28 又用 `glm-5.3-flash` 测过，同一个会话 id 发不相干的内容不会串会话；
  - 会话 id 的形状同官方新会话：带连字符的 UUID v7，前 48 位是生成时的毫秒数。记录在最后一次使用后保留 7 天，存在数据目录的 `sessions.json`，配置了 Redis 时再镜像一份，网关重启后照旧。以前的版本只在内存里记 2 小时，第二轮、网关重启后都会换 id，上游缓存断一次；
  - 不按号区分：换号重试、换号续聊都用这段对话原来的 id，按会话 id 缓存的模型（如 `glm-5.3-flash`）换了号也接得上缓存；按号缓存的模型换号还是要重算，所以换号时先回到用过的号（见上一条）。1.6.0 的会话 id 是按「号 + 内容」记的，升级后第一次见到升级前开始的对话，接着用它在这个号上的 id；
  - 推算出来的会话键不当作会话 id 发给上游。国际版上游不带这个头会直接拒绝。
- **`prompt_cache_key`**：网关不再自己生成，客户端带了就照转。官方客户端不发它，实测也没有让缓存命中变多（`glm-5.2` 每轮换新会话 id 时带上它反而更差）。
- **上游的对话轮记录**：上游按 `X-Conversation-Request-ID` 把一次用户发言里的所有调用（工具调用续轮、换号重试）记成一轮。客户端给了会话 id 时，按会话 id 和这一轮的用户消息认出这一轮，第一次认出时生成一个记在内存里，保留 2 小时；没给时每次用户发言新生成一个，工具调用续轮凭网关转出去的工具调用 id 找回它，所以开头逐字相同的两段对话也不会并成一轮。形状同官方：去掉连字符的 UUID v7。网关重启时正在进行的那一轮会拆成两条记录。
- **前缀缓存未命中的日志**：网关按对话对照上一轮。这段对话命中过、这一轮大前缀（1000 token 以上）却一点没命中时，记一行 `cache miss`：换了模型、换了号、会话 id 变了、消息比上一轮少（客户端压缩或改写了历史）是预期内的，记 `INFO` 并写明是哪一种；号和会话 id 都没变还是没命中，是上游没留住这段对话的缓存，记 `WARN`，带上距上一轮多久。每段对话 10 分钟内最多记一行；认不出是哪段对话的请求（没有会话键）不判断。上游有时在接近全命中时回「命中 0、未命中 3」而 prompt 有几万这种对不上的数，网关按 prompt 减未命中算命中，不当成整段未命中（命中率统计同样按这个口径）。
- 绑定有效期默认 30 分钟，每次使用滚动续期；配置了 Redis 时绑定会镜像过去（7 天 TTL），重启不丢。过期或重启后靠「回到用过的号」接上原来的号。
- 请求失败自动解绑；绑定的账号因某个模型限额而不可用时，换模型的请求会重新分配；绑定账号触到积分保底时也会解绑换号。

## 错误分类与账号处置

| 分类 | 触发条件 | 账号处置 | 恢复 |
|---|---|---|---|
| 余额不足 | HTTP 402 / 额度用完的业务码（`14001` `14012` `14013` `14014` `14018` `14019` `14022` `14023`）/ 余额关键词 | 冷却到**次日 04:00** | 签到或余额刷新发现余额恢复即解冻 |
| 频控 | HTTP 429 / 限流文案 | 软冷却 `soft_rate`，连续触发指数退避，封顶 `soft_rate_max` | 到期自动恢复，成功后清零退避 |
| 模型级限额 | `code 6000`–`6008`（按模型的 token、请求数限额，常见 `6004`） | 冷却到上游给出的重置时间（封顶 `soft_rate_max`）；**换别的模型照样可用** | 到点自动恢复 |
| 模型繁忙 | `code 14003`，以及每秒、每分钟限额 `6001` `6002` `6005` `6006` 没给重置时间时 | **只冷却这个号的这个模型约 30 秒**（上游给了 `Retry-After` 就按它），当场换号重试；所有号都挡住时回 429 + `Retry-After` | 到期自动恢复 |
| 会话太多 | `code 10105`（这个号同时进行的会话太多） | 账号冷却约 60 秒，当场换号重试 | 到期自动恢复 |
| 后端没有这个模型 | 400 / 404 + `code 11102` | 这个号的这个模型避开 6 小时（再撞翻倍，封顶 24 小时），当场换号；可选的号都避开时回 400 + `model_unavailable` | 到期放行重试一次；这个号用这个模型成功即清除 |
| 这类账号不能用这个模型 | 400 + `code 11158`（例如个人免费号调 GPT、Gemini、Grok；有使用者反馈国际版免费号调 deepseek 也是） | 这个模型加进这个号的[不接的模型](panel.md)名单，**一直不再派给它**（重启也记着），当场换号；可选的号都不接时回 400 + `model_unavailable` | 面板账号详情里解除；号升级后指定这个模型测活，测通也自动解除 |
| 上游排队中 | `code 6020`（上游这一路满了，把请求排进了队，带排位） | **不罚账号、不换号**，在这个号上照官方排队，到号后原样重发；合计等满 `pool.in_flight_wait` 或客户端断开就取消排队，回 503 + `upstream_busy`，带上游原文 | 即时 |
| 上游排队满 | `code 6021`（上游这一路容量排满了，换哪个号都一样） | **不罚账号、不换号**，回 503 + `upstream_busy`，带上游原文；客户端稍等重试 | 即时 |
| 这个号排队到上限 | `code 6022`（这个号排着队的请求太多） | 不罚账号，换下一个号；都回 6022 时回 503 + `upstream_busy`，带上游原文 | 即时 |
| 授权过期、未激活 | `code 14015` `14016` `14017` | 软冷却 `soft_rate` | 到期再试；补完激活后恢复 |
| Session 失效 | `12153` / `Offline user session not found` | **连续 3 次**才禁用（单次多为网络抖动） | 重新登录，或面板「解冻」 |
| 账号被风控 | 403 + `code 11140` + `request illegal`（「账号存在异常行为」） | 禁用这个号，原因里提示去官方申诉；同一个域短时间内多个号被限时**整域暂停**，见下文「风控波暂停」 | 向官方申诉，解除后在面板「解冻」；重新登录一般解不开 |
| 上游 404 | HTTP 404 | 固定冷却 60 秒 | 到期自动恢复 |
| 服务端错误 | HTTP ≥ 500 | 计入连续失败，达阈值熔断 | 熔断到期或成功后清零 |
| 上下文超限 | 400 / 404 / 413 + `code 11115` 或超限文案 | **不罚账号、不换号**（换哪个号都一样），原文返回 | 即时 |
| 请求体解析失败 | 400 + `code 11101` | **不罚账号、不换号**，原文返回 | 即时 |
| 内容拦截 | 400 + `code 11128` 或审核文案 | **不罚账号**，按下一节降级重试 | 即时 |
| 其他客户端错误 | 其余 4xx / 业务码非 0 | 不处罚，换号重试 | 即时 |

业务码的含义和归类照官方客户端（WorkBuddy 桌面端内置的 CLI）的错误码表；业务码比状态码和文案更可靠，先按它判。上下文超限的文案也照官方的词表认，覆盖各家模型供应商的说法。

客户端压缩过的请求体（`Content-Encoding` 为 gzip、deflate、br、zstd，或没标头但内容是 gzip）网关会先解开；解不开或不是合法 JSON 的请求就地回 400，不打上游。

**熔断**：所有冷却入口与 5xx 共用一个连续失败计数，累计达 `breaker_threshold`（默认 3）触发熔断，时长 `breaker_cooldown × 2^次数`，封顶 `breaker_cooldown_max`。成功即清零。

**测活提前恢复**：整个号在限流冷却、熔断中的号默认每 30 分钟被[测活](panel.md#测活)一次（发一条最短的真实对话），测通就提前解除冷却和熔断，不必等到期；也可以在面板上手动测。测不通照上表处置。

**软冷却退避**：同一账号连续触发软冷却时，冷却时长为 `soft_rate × 2^(连续次数-1)`，封顶 `soft_rate_max`。这个计数独立于熔断，只在成功或签到解冻时清零，随状态文件持久化。

**连败出池**：未知错误（传输层错误等）连败 `degrade_threshold` 次，临时出池 `degrade_cooldown`。

**风控波暂停**：上游有时会成批风控同一个域的账号（2026-10-23 下午国际版就出现过），这时继续轮换只会把剩下的号一个个送进风控。`restriction_wave_window`（默认 15 分钟）内同一个域有 `restriction_wave_threshold`（默认 2）个号被 `11140` 限制，网关就把该域其余未禁用的号暂停 `restriction_wave_pause`（默认 30 分钟），面板上显示为「风控暂停」。暂停期间这些号不参与选号，也不会在全部冷却时被拿来兜底；积分冷却这类截止更晚的冷却不会被缩短，暂停期间新来的更短的冷却也不会把暂停改短。到期自动恢复，账号池里点「解冻」可以提前恢复单个号。已经禁用的号再回 `11140`（比如[测活](panel.md#测活)复测被限制的号）不算新的风控，不计入。阈值设 `0` 关闭。另一个域不受影响。用了[代理池](proxy.md#风控波和-waf-按出口分开算)时按出口分开算：被限的号都在同一个出口，只暂停这个域里这个出口下的号；分布在几个出口，才暂停整个域。

## 系统提示词与内容审核

Claude Code、Codex 等客户端会在系统提示词里放固定模板句，上游内容审核按逐字匹配可能误拦（HTTP 400 + 审核文案）。网关有两层防护：

1. **提示词模式**（`prompt.mode`）处理系统提示词：

   | 模式 | 行为 |
   |---|---|
   | `passthrough`（默认） | 透传客户端原始系统提示词 |
   | `custom` | 删除客户端全部 system / developer 消息，换成网关自带的一条；用户、助手、工具消息逐字不动 |
   | `append` | 在开头连续的 system / developer 消息之后插入一条网关提示词，客户端原有消息逐字不动 |

   内置提示词约 2KB（[`internal/prompt/defaultprompt.md`](../internal/prompt/defaultprompt.md)）；`prompt.file` 可替换成你自己的。

2. **指纹脱敏**（`features.sanitize_blacklist_fingerprints`）清洗所有消息里的指纹串，系统提示词、用户、助手、工具消息，以及工具调用参数和推理内容都算。上游的「渠道指纹」拦截（400 + `code 11128`，`Illegal API invocation from an unapproved channel`）按大小写不敏感的连续子串匹配，网关处理这几类：
   - Claude Code、Codex 的固定模板句和 `x-anthropic-billing-header` 这类键值，改一个词或整段删掉；
   - 「You are … powered by / built on / created by …」这类自我介绍句，整句换成 `You are a helpful AI assistant.`；
   - DeepSeek Harness 的提示词：「… DeepSeek Harness Web GUI whose URL the runtime context names.」改个语序，正文里的 `DeepSeek Harness` 缩成 `DeepSeek`；
   - OhMyOpenCode 插件的 `Sisyphus-Junior - Focused executor from OhMyOpenCode`。

   后三类规则参考了 workbuddy2api-hub、workbuddy-manager、cpa-multi-plugins 等项目的实测（见 README 致谢）。

**降级重试**：请求被内容审核拦下时，网关判定为系统提示词误报，**在同一请求内**换成中性提示词重试一次；第二次仍被拦，说明是用户内容本身触发审核，如实返回给客户端。触发降级后到次日 00:00（北京时间）前，后续请求直接用中性提示词，不再先撞一次 400。降级状态只在内存里，重启清零。内容拦截不罚账号。

## 推理模型兼容

- **DeepSeek 思维链**：自动注入 `thinking.type=enabled` 与默认思考档位。
- **`reasoning_effort` 降级**：客户端要的档位该模型不支持时，自动降到最接近的可用档位。
- **`reasoning_content` 回填**：多轮对话里把上一轮的推理内容按上游要求回填到助手消息。
- `/v1/models` 透出每个模型支持的思考档位、默认档位、能否关闭思考，方便客户端按需选择。

## 原生工具调用标记还原

上游（DeepSeek 系）的工具调用原生语法是一段带**全角竖线**分隔符的标记文本（下面用 `<PIPE>` 代替两个全角竖线）：

```text
<PIPE>DSML<PIPE> calls>
<PIPE>DSML<PIPE> invoke name="exec_command">
<PIPE>DSML<PIPE> parameter name="cmd" string="true">ls -la<PIPE>DSML<PIPE> parameter>
</PIPE>DSML<PIPE> invoke>
</PIPE>DSML<PIPE> calls>
```

上游只在请求声明了 `tools` 时才把它解析成结构化的 `tool_calls`。而 `tools` 在中转链路上丢失是常态（协议转换丢字段、一次性探测、复核回合等），这时模型仍想调用工具，标记就以纯文本落进 `content`。Codex 这类只执行结构化调用的客户端会把它当普通正文，回合直接结束，工具一次都没跑。

网关在出站响应里把它还原成 `tool_calls`（流式与非流式都覆盖）：

| 工具名单 | 判定 |
|---|---|
| 非空 | 严格：块内每个工具名都必须在名单里 |
| 为空（`tools` 丢失） | 宽松：块必须完整闭合，且工具名是合法标识符 |

名单来自本次请求声明的工具和会话历史里出现过的工具名。另有三条前提：本回合上游没有给出任何结构化调用、块内不夹带正文、非流式要求 `finish_reason` 为 `stop`。**任何一条不满足都原样透出**，未闭合、参数畸形、超长（>256KB）一律不动。

命中与否各记一行日志，便于排查：

```text
INFO: [server] stream ...: repaired N native tool call(s) from assistant text (tool names known=K)
WARN: [server] stream ...: saw M native tool call block(s) but repaired none (tool names known=K)
```

## 流式输出

- SSE 帧按 OpenAI 规范**白名单重建**：保留 `reasoning_content`，工具调用按 index 合并，剥离未知字段。
- 保证恰好一个 `data: [DONE]`：上游漏发时补写；空流先写一帧 `error` 再补 `[DONE]`。
- 非流式请求由本地聚合为一个 `chat.completion` 响应，包含 `reasoning_content` 与 `tool_calls`。
- 还原工具调用时，一帧会拆成「正文帧 + N 个调用帧 + 收尾帧」，`finish_reason` 从 `stop` 改写为 `tool_calls`。
- 每个响应都带 `X-Request-Id`，可在面板请求记录里按它查找。
