# req HTTP/2 的 Chromium HPACK 差异

这是已在本仓库固定依赖副本中修正的上游能力差异记录，尚未向上游提交 issue 或 PR。基础 SETTINGS、优先级和解码后的头序相同，不能据此判定 HPACK 字节一致。

## 已复现

2026-11-16–17（台湾时间），调用 Trae 官方稳定 Linux 包中的 `@aha-kit/net` 和 `libsscronet.so`，只连接隔离的回环 TLS 服务，连续发送两次相同 POST。服务端使用空 SETTINGS，保持同一 HTTP/2 连接。测试凭证和设备 ID 均为虚构值。

官方 HEADERS 样本保存于 `internal/upstream/clienthello/trae-code-http2.bin`。读取两个请求的已解码字段，将包含请求 ID、trace 在内的全部字段原值交给网关，固定 authority、path 和正文，再比较 HEADERS block。这个同值重放用于比较编码器；原生 trace 生成已另通过固定输入原生向量与未修改运行时抓包校准，见官方客户端记录。

| 项目 | 官方 TTNet | 原版 req v3.61.0 |
|---|---|---|
| 首次 `:path` 编码 | 不加入动态表的 literal，名称索引 4 | 加入动态表的 literal，名称索引 5 |
| 该字段首字节 | `04` | `45` |
| 首次头块长度 | 291 bytes | 291 bytes |
| 第二次 `:path` | 再次发送不索引 literal | 引用上次动态表条目 |
| 第二次头块长度 | 87 bytes | 66 bytes |

在这份固定样本中，首次除 `:path` 的表示方式外，其余字段的编码相同；第二次还因路径占用动态表而使部分索引发生位移。两边都能解码出相同业务字段，属于传输身份差异。

## 源码位置与处理边界

req v3.61.0 的 `internal/http2/transport.go` 中，`ClientConn.writeHeader` 直接调用 `hpack.Encoder.WriteField`。现有公开接口可配置 SETTINGS、窗口、优先级及头顺序，没有按字段控制动态索引的入口。

`Sensitive=true` 表示 never-indexed，并不等于上述 without-indexing；只设置这个标志仍不能得到相同字节。也不能只改第一次的一个字节：编码器自身的动态表状态必须同步保持一致，否则后续请求会解码错误。

本仓库在 `third_party/req` 保留 MIT 的 req v3.61.0 完整运行源码和原版权／许可，以根模块 replace 引用，增加默认关闭的 `SetHTTP2PathWithoutIndex`。非静态 `:path` 绕过动态表，使用 without-indexing literal 和静态名称索引 4；Huffman 继续使用 Go HPACK 的实现。固定伪头顺序确保待处理的表大小更新在路径之前发送。不修改系统 Go 模块缓存。

修正后，同一 fixture 连续两次请求的 HEADERS block 分别为 291 和 87 bytes，均与官方逐字节一致。`TestTTNetOfficialHPACKBytes` 将此比较保留为回归；固定依赖中的独立测试另验证短／长路径、Huffman 选择、动态表不被路径污染、服务端表大小 0／64／4096 时后续字段和第二次请求仍能正确解码。

## 连续请求与表大小补采（2026-11-17）

分别使用未修改网络栈的 TTNet、Work 同版 Chrome 156.0.8078.79 和 Electron 39.2.7 `net.fetch`，在仅启用回环的隔离网络中发送八次连续 POST。路径、查询参数及字段值发生变化，TTNet／Auth 还包含约四千字节的虚构字段值，TTNet 另有超过默认 4096 容量的六千字节字段，用于观察表淘汰后的重用。Work 样本来自引导页的简单 fetch，重放保留其实际字段顺序，只验证编码器；线上 Work 应用头序继续依据公开站点 NetLog，不能把简单 fetch 的头序直接覆盖过去。

三套运行时都对非静态 `:path` 使用 without-indexing，现三条 Trae profile 均开启该设置。Work／Auth 另有服务端先发空 SETTINGS，随后依次下发 `HEADER_TABLE_SIZE=64 → 0 → 4096` 的样本。

| 场景 | 官方样本 | 原实现差异与修正 |
|---|---|---|
| TTNet 八请求，包含上述 SETTINGS 变更 | 收到 ACK，但未观察到发送表大小更新，仍使用原表动态索引 | 本次逐字节匹配；没有把它判作小表兼容性通过，也没有据此外推其全部 SETTINGS 行为 |
| Work／Auth，默认 4096 表 | 路径不入表，后续其他字段正常重用与淘汰 | 补开路径设置后，连续八请求匹配 |
| Work／Auth，64／0／4096 | 后续头块发送 table-size-update，缩表后重发字段，再恢复索引 | req 原来忽略服务端 HEADER_TABLE_SIZE，按 profile 开启跟随；这一阶段仍受默认 4096 上限约束，后续扩容修正见下节 |
| TTNet／Work／Auth，字段超过当时表容量 | 仍使用 incremental indexing，插入超大字段会按 RFC 7541 清空旧表 | Go HPACK 原来改用 without-indexing、不清旧表；只跟随大小仍不能得到相同后续字节 |

为解决最后一项，固定依赖另保留 `golang.org/x/net v0.57.0/http2/hpack` 的运行源码和原 BSD 声明，增加默认关闭的 `Encoder.IndexOversized`；只修改原编码器的入表判定，动态表、Huffman 与整数编码继续使用原库。三条 Trae profile 均开启 `SetHTTP2IndexOversized`，Work／Auth 另开启 `SetHTTP2RespectHeaderTableSize`；两项独立配置，TTNet 不因超大字段修正改变本次采样的 SETTINGS 行为。没有自行重写 HTTP/2 连接池或从模块缓存打补丁。

回归用相同字段值及顺序逐字节比较：TTNet 原两请求加两组新八请求、Work 两组各八请求、Auth 两组各八请求，共 50 个头块均匹配。fixture 为 `trae-code-http2{,-dynamic,-oversized}.bin`、`trae-{work,auth}-http2-{dynamic,settings}.bin`。固定依赖的补充测试使用标准 x/net 解码器，覆盖 0／64／4096 容量下的超大字段、清表后重复字段及敏感字段；Clone 保留开关且不共享可变设置。

## 初始表与大表补采（2026-11-17）

再次独立运行上述三个官方运行时，分别以 `HEADER_TABLE_SIZE=0／64／8192／1048576` 作为服务端首个 SETTINGS，并增加 `8192 → 64 → 16384 → 0 → 8192` 连续变更场景。每场景八次 POST，Auth／TTNet 使用约 5400 与 7000 字节的虚构字段；服务端每次等待 SETTINGS ACK 后才放行响应，保证下一次请求在该更新之后发出。三个运行时各五组，全部请求正常结束。

| 场景 | Work／Auth | TTNet |
|---|---|---|
| 初始 0／64 | 缩表，并按容量编码后续字段 | 即使收到 ACK，样本仍使用原 4096 表，没有 table-size-update |
| 初始 8192／1048576 | 发出相应 table-size-update，Auth 能重用超过 4096 的字段 | 同上，不跟随这组初始值 |
| 连续扩容、缩容、禁用和恢复 | 发出 64／16384／0／8192 更新，淘汰和后续索引随之改变 | 收到五个 ACK，仍使用原表；不能据此标作对小表服务端兼容 |

这轮复现了网关的实际差异：仅调用 `SetMaxDynamicTableSize` 会被 Go HPACK 的默认上限 4096 截断。Work／Auth 现同时按服务端值更新 `SetMaxDynamicTableSizeLimit` 和当前大小，不再截断已允许的扩容；未给 TTNet 开启这个策略。1 MiB 是已采样值，未确认该官方版本的最终容量上限。

首个 SETTINGS 与在途首请求的处理顺序可能不同，官方多次运行也会将首次 table-size-update 放在第一或第二头块；不将这一时序固定为 fixture 的唯一取值。新增回归用前两个请求建立各自表状态，从第三次起比较完整头块，保留之后所有大小更新、超大字段重用和清表后的索引检查。15 组新增样本共 120 个头块，其中 90 个稳定阶段头块逐字节匹配；连同此前 50 个，共比较通过 140 个完整头块。修改前大表／连续扩容回归失败，修改后全部通过。fixture 为 `trae-{code,work,auth}-http2-initial-{zero,small,large,megabyte,resize}.bin`。

固定依赖全量普通测试与 HTTP/2／HPACK race、根模块全量普通测试、相关 upstream／providers race、build、vet、golangci-lint 和格式检查通过。相关包 race 跳过此前已确认触及两秒上限的既有 `TestListingModelsDevFailuresSilent`，没有将全量 race 记作通过。解码器从协议默认 4096 起步，仅放宽允许的表大小至 1 MiB，避免把“可接受的上限”误当初始动态表容量。

修正已保数据更新至 dev，健康检查及实际服务容器内的 Work／Code 流式正文与结束帧通过。重建前后及请求后，配置、auth 文件、完整账号凭据和账号设置一致；重建前后绑定完全一致，请求后复用的两条绑定仅正常续期，账号和上游会话 ID 保持。严格摘要报告保留该到期时间差异，已用停机备份逐字段确认，没有回填旧凭据或设备身份。这轮没有重复发起 Qoder 推理。

## Work／Auth 连接级 DATA 队列（2026-11-17）

HPACK 以外的确定差异继续由固定副本处理：增加默认关闭的 `SetHTTP2ChromiumUpload`，只在 Work／Auth 开启。依据是相应 Chromium 156.0.8078.79／142.0.7444.235 的 SpdySession／SpdyStream／SpdyWriteQueue／SpdyHttpStream，以及六轮官方固定正文样本。每流最多排一个 DATA，同优先级 FIFO，排帧时预留连接／流窗口，写完成后读取并将下一帧放到队尾；同步写循环期间收到的补窗在可写队列排空后处理，取消和连接错误仍可打断等待。取消未写出的排队 DATA 归还窗口；空结束帧的窗口等待后续已修正，见下节。长度超限、读取错误及补窗溢出保留原始错误。

## 空结束 DATA 仍须等正窗口（2026-11-17）

此前让空结束 DATA 绕过零窗口，属于与官方客户端不符的实现和测试预期。Chromium 的 `CreateDataBuffer` 在处理零长度前先检查两个窗口。Work／TTNet 独立官方样本证明：一个字节耗尽初始流窗口后，即使来源已结束，零窗口或经 SETTINGS 缩至负一的窗口仍不发送 DATA；分别补一个或两个字节使窗口为正后，才发送空 END_STREAM。

固定副本现让 Work／Auth 的队列在零／负窗口等待，避免负额度用于切片。TTNet 的原 writer 发送独立空结束 DATA 前，通过已有的 `ChromiumFlowControl` 等待正窗口；等待时释放写锁。空帧本身预留零额度，非空 trailers 继续使用不受 DATA 流控的 HEADERS。req 未开启该配置时沿用原行为。

旧网关四场景均复现差异，Work 负窗口场景还复现切片越界 panic。修正后两轮、八份网关样本与十份官方样本的 DATA 长度、END_STREAM 及补窗先后匹配；新增根模块八场景回归覆盖补窗完成与取消，三轮 race 通过，固定副本补充连接／流零窗口、负窗口及 trailers。详见[官方客户端记录](official-client.md#空结束-data-的零窗口与负窗口等待2026-11-17)。这不扩大到尚未完成的完整异步调度。

## TLS pending 期间处理上传事件（2026-11-17）

两轮官方 Work／Auth socket 背压样本确认：SSL 写入 pending 时，另一流收到补窗能在当前大上传结束前恢复；旧网关两轮均等到大上传结束。现于 Work／Auth 的 Unix TCP 下接入 Chromium 同容量的 17 KiB 有界密文缓冲，区分 TCP EAGAIN、BIO 仍可接收和 TLS 真正等待空位。短命 worker 只在实际 EAGAIN 后运行，排空即退出；部分写、关闭、截止时间和异步错误保留来源。

固定副本的 `uploadEvents` 合并 WINDOW_UPDATE 与后台正文读取完成事件。同步写循环期间排队，TLS pending 回调触发时按 FIFO 处理，恢复可写流；输入被 TLS 接收后恢复同步状态。读取返回零字节后的异步重试同样入队；已取消的正文事件不复活上传，补窗溢出维持流／连接级错误。两轮网关复采的 Work／Auth 均恢复正确先后，正文及响应完整。

新增固定副本回归检查 pending 恢复 B 的 FIFO、读取／补窗顺序影响流控结果、零字节重试没有绕开事件队列。根模块用真实 TCP、TLS 和两流正文检查实际背压，另验 deadline／close 唤醒；原固定正文精确分片回归保持。依据与样本条件见[官方客户端记录](official-client.md#socket-背压期间的补窗与正文事件2026-11-17)。

## PING／SETTINGS ACK 进入连接队列（2026-11-17）

继续复采发现，原读循环处理 PING／SETTINGS 时等待 `wmu`，背压中的后续补窗因此被压住。两轮官方 Work／Auth、两种控制帧共八份样本在恢复读取后均先 ACK、紧接 B 的 DATA；旧网关八份在 ACK 后均继续 A。固定副本现把两者加入上传事件 FIFO 和优先于 DATA 的控制队列，读取不等待 socket；TLS pending 时仍按事件先后恢复可写流。控制写失败保留来源并关闭连接、唤醒等待正文。

Chromium 上传路径的 SETTINGS 与 HPACK 编码都用连接锁保护，不再要求接收处理获取网络写锁；帧正文独立复制，表大小变更继续由原编码器按协议在下一头块发出。两版本官方源码的默认控制队列上限为 10000、入队前比较 `>`，新队列按此限制待处理的 PING／SETTINGS ACK；PING 压力样本已确认这两个运行时均在第 10002 个积压帧触发上限关闭，但官方先发出已排队的 10001 个 ACK，当时网关直接关闭、未排空 ACK；该确定差异在 2026-11-18 继续修正，不能把边界匹配算作完整压力通过。

修正后两轮八份网关复采均为 ACK 后先发 B、正文和响应完整。新增真实 socket 与固定副本回归涵盖读取继续处理、ACK／DATA 顺序、失败退出、帧缓冲复用、连续表变化和两种队列状态的上限；旧固定正文与 HPACK 样本继续保留。HEADERS／RST_STREAM／出站 WINDOW_UPDATE／GOAWAY、TTNet 等其余调度尚未全部覆盖，见[官方客户端记录](official-client.md#pingsettings-不阻塞后续补窗2026-11-17)。
