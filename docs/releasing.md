# 发版与版本号

本仓库从 1.0.0 起按[语义化版本 2.0.0](https://semver.org/lang/zh-CN/)独立编号，不再沿用上游的版本号。版本号写在 `cmd/server/main.go` 的 `appVersion`，每一版的变更记在[更新日志](CHANGELOG.md)。

- [什么时候用预发布或正式版](#什么时候用预发布或正式版)
- [发版步骤](#发版步骤)
- [更新日志的格式](#更新日志的格式)

## 什么时候升哪一位

| 改动 | 升哪一位 | 例 |
|---|---|---|
| 不兼容的改动，升级要手动处理：配置项改名或删除、旧配置不能沿用的默认行为变化、接口返回结构不兼容、镜像路径或启动参数变化 | 主版本号 | 1.4.2 → 2.0.0 |
| 向下兼容地新增功能：新视图、新配置项、新接口、同步上游带来的新能力 | 次版本号 | 1.4.2 → 1.5.0 |
| 向下兼容的问题修正，以及文案、样式之类的小调整 | 修订号 | 1.4.2 → 1.4.3 |
| 只改 CI、文档、测试，使用者感觉不到 | 不升 | — |

- 升主版本号时次版本号和修订号归零，升次版本号时修订号归零。一次推送里有多种改动，按最高的那一级升。
- 合并上游时，上游自己的版本号不影响本仓库：`appVersion` 冲突一律保留本仓库的值，上游版本只记在[同步记录](upstream.md#同步记录)里。同步带来使用者看得到的变化时，按上表升版本号，并在更新日志里写「同步上游至 `xxxxxxx`：……」。

## 什么时候用预发布或正式版

先按上一张表定目标版本，再按本次试用要验证的内容选渠道。以下以目标版本 `1.14.0` 为例。

| 版本 | 什么时候选 | 本轮重点 |
|---|---|---|
| `1.14.0-alpha.1` | 功能刚有可运行的实现，接口、配置或使用流程还可能调整 | 邀请少量开发者验证方案和核心路径 |
| `1.14.0-beta.1` | 计划交付的主要功能已可用，仍需要不同用户和环境检验兼容性 | 收集部署、升级、客户端接入及日常使用的反馈 |
| `1.14.0-rc.1` | 本次交付范围已定，维护者认为这份代码可以作为正式版，剩下的是发版验收 | 用候选包核对安装、升级、关键回归和已知限制 |
| `1.14.0` | 正式支持范围内的验收已通过，影响正常使用的阻塞已解决，实验功能的边界已写明 | 面向常规部署发布，推进正式更新渠道 |

渠道可按需要选用。已验证的小修复可以直接发正式修订版；范围已定、只需验证安装包的新功能可以直接从 RC 开始。维护者按实际验收结果选版本，Actions 按 `appVersion` 分发产物。

同一阶段发布新代码时递增序号，例如 `rc.1 → rc.2`。同一提交仅因 CI 或上传失败而重跑，沿用原编号。候选版本验收通过后去掉后缀，`1.14.0-rc.2 → 1.14.0`；后续兼容修复才用 `1.14.1`。正式版更新日志应汇总自上一正式版以来的用户可见改动，方便跳过预发布的用户了解升级内容。

## 发版步骤

推送即发版，不手动打 tag：

1. 改完代码，按上表定好新版本号，改 `cmd/server/main.go` 的 `appVersion`。
2. 在 `docs/CHANGELOG.md` 顶部加这一版的条目（格式见下节），日期写推送当天。
3. 提交并推送到 `main`，提交信息按[提交规则](commits.md)写，发版提交是 `chore(release): x.y.z`。CI 先检查这次推送的提交信息，再依次跑 `gofmt` 检查、`go vet`、`golangci-lint` 和 `go test`（命令见[从源码构建](deployment.md#从源码构建)），任何一步失败都不打标签、不建 Release、不推镜像；`go test` 还会核对 `appVersion` 与更新日志最新一版一致。

### 触发和产物

| 入口 | 执行与产物 |
|---|---|
| 只改说明文档、反馈表单、Issue 自动化或 PR 模板的 PR | 检查提交信息与仓库脚本。更新日志和随包分发的 README 仍走完整构建 |
| 代码、依赖、打包或发布流程 PR | 检查前端、Go 和 Windows 持久化，生成五平台包供下载，验证 Docker 构建；仅产生 Actions artifacts |
| Actions 中手动运行 `go-binaries` | 可选择分支或标签做完整验证，产物在该次运行的 Artifacts 中 |
| 推送到 `main` | `main-release` 将每次推送排队。五个平台打包成功后才推镜像，镜像成功后上传版本 Release，最后更新滚动下载 |

| 源码版本 | GitHub Release | GHCR 镜像 |
|---|---|---|
| 新正式版，例如 `1.14.0` | 创建带版本号的 Release、五平台包和校验清单，并推进 Latest 和固定下载链接 | 完整版本、`1.14`、`1`、`latest`、`main` 和短 SHA |
| 新预发布版，包括 alpha、beta、RC | 每个完整版本有自己的预发布 Release 和校验清单 | 只推完整版本标签，例如 `1.14.0-rc.2` |
| 新提交沿用已发布的版本号 | 正式版只更新滚动下载；预发布版只验证构建 | 正式版只更新滚动标签及短 SHA；预发布版只构建 |

正式 Release 的「完整变更」从第一父提交链上最近的正式版本起算，预发布从上一版本起算。面板运行正式版时只提示正式更新。

发版中断时，在 **Actions → main-release → 对应推送 → Re-run failed jobs** 补跑。每个发布任务都会重新核对远端标签和 `main`。同一提交留下的草稿会补传文件再公开；已经完整发布的编号下载包保持原样。版本标签已属于其他提交时，请更新版本号；旧提交的重跑只补本版本产物，滚动标签继续指向较新的正式构建。已脱离 `main` 历史的提交只做验证。

面板的[一键更新](panel.md#一键更新)直接下载这个 Release 里的 `wb2api-panel-vx.y.z-<系统>-<架构>.tar.gz`（包的根目录要有 `wb2api`）和 `checksums.txt`，再用 `wb2api -version` 试运行。改打包方式、文件名，或去掉 `-version` 参数，都会让一键更新失效，要同步改 `internal/selfupdate`（测试会核对工作流里的包名和打包命令）。推送后到 Release 建好之前点一键更新，会提示 CI 还在构建。

## 更新日志的格式

格式参考 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)。面板的更新提醒、升级后的「本次更新」和 Release 说明都从这份文件解析，所以下面几条要守住：

- 版本标题写成 `## [x.y.z] - YYYY-MM-DD`，版本号不带 `v`，新版本写在最上面。`[未发布]` 这类不是版本号的标题会被跳过。
- 分组标题用 `### 新增`、`### 变更`、`### 弃用`、`### 移除`、`### 修复`、`### 安全`，没有内容的分组不写。
- 条目以 `- ` 开头，写给使用者看：做了什么、在哪里用、要不要手动处理，不写实现细节。一条写不下时，续行缩进两格。
- 需要整体说明的（如升级注意事项），写在版本标题和第一个分组之间。
- 行内只用反引号代码和链接。链接到 `docs/` 里的其他文档用相对路径，面板和 Release 说明会补成 GitHub 上的地址。

网关每 6 小时读取一次 `main` 分支上的这份文件（见[更新提醒](panel.md#更新提醒)）。推送后到镜像构建完成之间有几分钟空档，这期间检查到新版本的用户，可能要稍等一会儿才能拉到新镜像。
